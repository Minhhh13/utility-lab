# Viewed-photo caching

The production package includes the local stills used by the five-step walkthrough. They load on demand. When Aim detail magnifies the existing aim photo, the browser reuses that image. The packager checks that every referenced local still was copied before publication. Players can download the optional offline photo pack from workspace settings.

Zooming into a supported photo loads a higher-resolution frame from the same recording. The collection covers 47 first-person standing views and 20 landing views across all eight maps. The gallery keeps the displayed image in place until the browser decodes the matching original and confirms its dimensions. Fit returns to the lightweight view. Existing high-resolution publisher photos, including the two 2560×1440 Anubis Window molly aim shots, open at their supplied resolution. [Frame and resolution evidence](data/source-photo-resolution.json)

Utility Lab uses browser storage and the existing static CDN. No server-side image proxy, database, scheduled scraping or video download is added.

The app shell, hashed map catalogues, maps, fonts and bundled photos already use the service worker's same-origin asset cache. Only the chosen map catalogue loads; it also stays in memory during navigation. Publisher images retain their normal HTTP cache behavior. A sampled CS2Tricks CloudFront WebP advertises a one-year immutable cache; a sampled CSNADES image has no Cache-Control header. Both samples lack cross-origin read permission for utilitylab.au, so fetching their image bytes into the app with CORS is not a reliable option.

The service worker now keeps at most **12 successfully viewed publisher photos for seven days** in an independent Cache Storage cache. It reuses the response from the actual image request and waits for the browser image's load event before persistence. That confirmation matters: a no-cors response is opaque, so HTTP success alone cannot distinguish a real image from a missing/error page. Pending responses are also bounded to 12 and expire after two minutes. Confirmations belong to the requesting browser client and response token: one tab's decoded image cannot confirm another tab's failed response, and an old confirmation cannot persist a newer unvalidated response. Slow storage queues retain keys/tokens rather than an unbounded queue of image bodies.

Nothing is downloaded merely by browsing map pins. Video, arbitrary image hosts, URLs carrying query credentials and non-image requests bypass this cache. Only the current primary publisher image hosts and paths qualify: CS2Tricks CloudFront, CSNADES, NadesDB and the new setpos.gg render images. New source recipes load their photos only when opened, rather than prefetching the catalogue.

Reopening a confirmed photo can use the browser cache offline without another publisher request. Old entries expire and the least recently used photo leaves storage when the 12-photo bound is reached. Storage/permission/quota failures are best effort and never block displaying the original image. A retry first evicts any failed entry, waits for worker acknowledgement, then bypasses the HTTP cache once for that client. Another tab cannot consume that retry or lose its own pending image. Orphan metadata is removed along with images. App-shell updates preserve this independent cache. The cache is disposable performance data; personal uploaded photos and backups remain in their existing IndexedDB store.

After the current photo loads, the gallery warms only its next adjacent slide. `photo-preload.ts` uses a low-priority image request through normal HTTP caching, keeps at most three image objects and cancels unfinished evicted warmups. It honors data saving and slow-2G/2G connections. The caller does not iterate the catalogue or warm video files.

Opaque responses may consume more browser-reported quota than their transferred image size, so the entry limit is intentionally small. The cache adds no application-server/database work and performs no proactive revalidation or provider polling. A source photo can remain cached for up to seven days; newly versioned publisher URLs naturally create a new entry.

Verification: ten focused service-worker cases cover decode-gated persistence, offline reuse/no duplicate fetch, failed-image retry, TTL/LRU limit, slow-storage bounds, same-URL response generations, cross-client isolation, quota/storage failure, excluded URLs/video, and preservation across app-shell updates. Two browser cases exercise a real worker plus opaque remote image responses, including an invalid-image retry; the final release gate reruns them against the integrated candidate. Header observations are evidence from 24 November 2026, not a promise about future publisher configuration. Local browser/trace measurements are laboratory observations rather than field Core Web Vitals or evidence of actual Steam-overlay/iPhone performance.
